### 已证实的差距

**A. 两个报告标志**：两个独立 string 事实（非 boolean），
allowedValues=["0","1"]，nullable=true/indeterminate。
主来源 §1.3 前提3 要求组合语义；confirmed 候选拆成独立事实但未在
条件表达式中显式编码组合语义。待定条件 = 任一标志为空的情形。
未运行求值器 → 标记为静态表达式核查。反例：("0",null)→有、("1","1")→无。

**B. 空值策略**：order.amount 与特殊申请计数均为 nullable=true/indeterminate。
如未来需要"空值→0"语义单列建议。

**C. report.merge_group_eligible** = source boolean / nullable=false / fail；
mappingCandidate 仍为 unresolved，物理来源及产生方式尚未确定。
其逻辑描述包含组合业务语义，但不能把描述当作实现证据。

**D. R1**：count>0 本身不是缺陷；缺陷是 filters.items 仅含任务键过滤——
当前契约没有计数专用过滤字段，未结构化表达申请类型和审批状态等计数范围。
OA 执行层事项（触发、调度、回调写入）不属于候选查询要求范围。
验收：类型匹配且已审批 / 类型匹配但未审批 / 类型不匹配 / 无匹配记录四组。

**E. R3**：confirmed 候选 R3 = `_compare("product.special_product_flag","eq",True)`——
仅检查特殊产品标志，缺少主来源要求的复合金额条件。
最小复现（脱敏）：标志为真但复合条件为假，当前候选仍会命中 READY。
具体数值测试留给后续经授权的 RuleReader 修复任务。

**F. R4**：有数据/已释放与日期口径冲突，局部待决，不扩大为全 V3 阻塞。

**G. 已归档交付覆盖完整报告侧 eligibility 顺序**：
R0→R1→R9→R4→R2→R3→R8→R5→R6→R7
（5 stages: 前提终止=1, 前提=6, 报告规则=10, 合并组=1, OA 范围=1）。
