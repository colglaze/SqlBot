### 1. 下游对象版本表

- **proposed**：采用 DEV §4.3 版本表——`FactBindingRequest.contractVersion = 3.0.0`；
  `SqlTemplateCandidateV3.schemaVersion = 3.0.0`；
  `HandoffClosureV3`/`ProjectBindingContextV3`/`GovernedMetadataSnapshotV3`/`ApprovalRecordV3`/
  `ResolveMetadataRequestV3`/`BindingResolutionReportV3`/`GenerateSqlCandidateRequestV3`/
  `ValidateSqlCandidateRequestV3`/`SqlStaticValidationReportV3`/存储包装首版均为 `1.0.0`；
  `ruleRef.schemaVersion="3.0.0"` 表示上游规则契约版本。共 12 个独立顶层契约对象。
- **理由**：延续对应 V2 对象的既有版本先例，自身契约独立演进；`SqlTemplateCandidateV3` 采用 `3.0.0`
  延续候选契约与生成管线世代对齐的既有先例；避免机械继承 FBR 版本号。
- **替代方案**：所有下游对象机械继承 `3.0.0`（被否决：会混淆"自身契约版本"与"所引用规则契约版本"，
  破坏版本独立性）。
- **风险**：版本号数字相同（`1.0.0`）可能引起误解；通过明确"自身契约 vs 所引用规则契约"分界缓解。
- **批准后下一动作**：当前已作为 proposed 写入 REQ/BIZ/DEV；用户批准后更新文档状态，
  M1 契约测试绑定各对象 `schemaVersion`。

### 2. context/snapshot 批准记录载体与信任边界

- **proposed**：采用 DEV §3.3 的 `ApprovalRecordV3` 结构（`approval_id` 是不透明稳定 ID，**不是
  SHA-256**；`context_ref`(context_id, context_version, sha256)/`snapshot_ref`(snapshot_id,
  snapshot_version, sha256)/`policy_version`/`actor_ref`(wire actorRef)/`approved_at`/
  `content_sha256`），insert-only，独立于 SQL 候选审批。
- **理由**：metadataReview 是批准 owner，SqlBot 是契约实现 owner；需要不可变审计记录精确绑定
  context/snapshot 的 ID、版本和内容哈希（三要素缺一不可）。
- **信任边界分层**：M1 只负责内容闭包校验（格式、哈希、引用、声明状态内部一致）；
  真实 M3/M6 还需受信批准来源核验（DEV §3.6）——通过受控只读端口按 approvalId 取得 metadataReview
  登记的记录并逐字段比对；元数据内容已确认不等于任意客户端 JSON 已获运行授权。
- **替代方案**：复用 V2 的 `approvalRef` 字段（被否决：V2 的 approvalRef 仅是一个引用，不包含
  完整的版本链和载荷哈希，无法满足 V3 独立契约链的审计要求）。
- **风险**：批准记录存储设计（MongoDB 集合/索引）在 M6 编排前才冻结；早期可能需迁移。
- **批准后下一动作**：当前已作为 proposed 写入 DEV §3.3/§3.6；用户批准后更新文档状态，
  M1 契约测试覆盖其字段，真实 M3/M6 核验实现按 §3.6 门禁要求另立阶段。

### 3. V3 独立契约链

- **proposed**：采用 BIZ 第 1 条决策——V3 下游是独立契约链，不是 V2 链的扩展；禁止 V3↔V2 转换、
  包装或降级；V2 链行为逐字节不变。
- **理由**：V2/V3 字段集互不相交、双向严格解析必然失败、上游禁止降级；不存在合法 V3→V2 桥。
- **替代方案**：在 V2 链中增加 V3 适配层（被否决：违反 BIZ 第 1 条，会吞掉 V3 五阶段/优先级/多
  outcome 语义）。
- **风险**：V3 需独立实现完整链路（Phase 2G→3→4→存储），工程量较大；通过 M1–M6 分阶段交付缓解。
- **批准后下一动作**：当前已作为 proposed 写入 BIZ；用户批准后更新文档状态，M1 开始实现 V3 专属模块。

### 4. 复杂事实拆分责任

- **proposed**：Agent 1/businessRuleReview 负责业务表达和派生语义（包括 R5/R6/R7/R8/合并组的
  业务条件）；Agent 2 只为 source/aggregate/exists 基础事实生成单事实 SQL；不假设数据库存在
  `*_eligible` 物理列；集合型或复合条件必须在上游 vNext 中拆分为可追溯基础事实。
- **理由**：AST 只能证明参数/对象/列/join/`fact_value` 来源，不能证明规则业务语义；复杂布尔事实
  必须由规则执行层表达。
- **替代方案**：Agent 2 直接消费预计算 `*_eligible` 布尔列（被否决：当前 handoff 的
  `mappingCandidate` 为 unresolved，现有已核验证据没有提供可授权的物理映射；不得假设存在
  对应物理列，且会把业务规则藏进不受校验的自然语言说明中）。
- **风险**：上游 vNext 交付延迟会影响 M3 输入可生成性；通过 BUG-02 跟踪并独立裁决 R4 缓解。
- **批准后下一动作**：当前已作为 proposed 写入 BIZ/DEV；用户批准后更新文档状态，上游 vNext 启动。

### 5. M1–M6 实施顺序与真实调用门禁

- **proposed**：采用 DEV §12 里程碑分层——离线 M1–M3 使用合成 fixture/fake provider，不依赖真实
  数据库或在线授权；真实 M3/M6 必须等待 BUG-02 新版本 catalog/rules/handoff、已批准
  context/snapshot/grants、同次 MongoDB 仓储背书、provider 配置和当次在线授权。
- **理由**：离线开发可并行于上游 vNext 和批准流程；真实调用必须满足全部门禁。
- **替代方案**：所有里程碑都等真实 batch 落库后再开发（被否决：严重拖慢进度，且离线测试不依赖真实数据）。
- **风险**：真实 M3/M6 启动时间受上游 vNext 和批准流程影响；通过提前准备合成 fixture 缓解。
- **批准后下一动作**：当前已作为 proposed 写入 REQ/BIZ/DEV；用户批准后更新文档状态，M1 开工。
