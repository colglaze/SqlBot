# BIZ-20260818-01：规则与 SQL 生命周期

- 状态：`proposed`
- 创建日期：2026-08-18
- 影响需求：[REQ-20260818-01](../requirements/REQ-20260818-01-release-rule-sql-generator.md)

本文件区分“用户已明确的基线”和“为推进 Phase 0 暂定、仍需确认的决策”。未确认项不能静默升级为生产事实。

## 已明确的基线

### D-01 MongoDB 是规则和 SQL 版本来源

系统从 MongoDB 获取 JSON 格式的释放规则，也能获取旧版本规则和旧 SQL。批准后的新版 SQL 写回 MongoDB。

### D-02 历史规则和 SQL 用作生成模板

生成新 SQL 时同时参考旧规则与旧 SQL，以保留仍适用的关联、字段和方言习惯，并明确移除已经删除的条件。

### D-03 人工审核是强制门禁

自动生成的 SQL 只有经过人工审核才能写入已批准/已发布版本。自动测试不能代替业务审核。

### D-04 复杂 SQL 可以分解为临时表方案

当单条 SQL 可能超时，可以构建临时表分阶段处理。是否有临时表权限、具体语法和事务行为必须按目标数据库确认。

## 暂定决策

### D-05 目标集合暂定义为“不满足条件的未释放记录”

暂用：

```text
exception_set = unreleased AND NOT(release_eligible)
```

理由：原始描述最接近“查询所有未满足条件的未释放数据”。

待确认的另一种合理解释是：

```text
actionable_set = unreleased AND release_eligible
```

后者表示“已经满足释放条件、但还没释放”的待处理记录。两者的 `NOT` 恰好相反，必须由业务负责人确认。确认前，规则解释器和 SQL 生成不得投入生产。

### D-06 规则和 SQL 采用不可变版本

批准版本不原地覆盖。任何变化创建新 `rule_version`/`template_version` 并引用父版本。这样可以还原生成输入、审核证据和回滚基线。

### D-07 一个规则版本对应一个目标类型

`project_report` 和 `raw_data` 分别版本化、生成、审核和发布，避免一个目标的变更意外影响另一个目标。需要跨目标原子发布时另立需求。

### D-08 当前规则优先于历史 SQL

历史 SQL 是示例，不是权威。如果旧 SQL 包含当前规则已删除的条件，候选必须删除该逻辑；如果当前规则无法映射到 Schema，系统必须阻塞而不是沿用旧 SQL。

### D-09 批准对象包括完整执行计划

人工批准的不是单个字符串，而是 SQL 方言、查询/阶段列表、绑定参数、输出契约、Schema/上下文版本、覆盖矩阵和验证报告的整体。批准后任一部分变化都需要新 revision 或新版本。

### D-10 生成与执行解耦

v1 首先交付“生成—验证—审核—发布模板”。是否由本服务正式执行发布后的 SQL 尚未决定；验证阶段只允许 `EXPLAIN` 和受限试跑。

## 版本选择规则

- 基线范围：相同 `project_id + target`。
- 首选：当前活动的 `published` 版本。
- 没有 published 时：可以冷启动，但显式记录 `baseline_mode = none`。
- 规则或项目上下文的内容哈希变化会使尚未批准的候选过期。
- 发布使用父版本比较交换：活动版本仍等于候选的 `parent_template_id` 时才成功。

## 需要业务负责人确认

| 问题 | 影响 | 当前默认 |
| --- | --- | --- |
| 异常集合的 `NOT` 方向 | 所有结果正确性 | `unreleased AND NOT(eligible)` |
| 释放状态如何判定 | 基础过滤和空值语义 | 无默认，缺失即阻塞 |
| 报告和原始数据是否独立发布 | 版本粒度 | 独立 |
| 审核角色与权限 | 谁能批准/发布 | 需要具名人工审核者 |
| 是否允许审核例外绕过试跑 | 安全门禁 | 不允许 |
| 服务是否执行正式查询 | 部署和权限范围 | v1 暂不负责 |
