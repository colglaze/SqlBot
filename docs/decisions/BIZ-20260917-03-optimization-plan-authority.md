## 决策

1. 当前报告释放（及优化方案中的原始数据释放）的**业务判定权威**是优化方案 §1.3 结构 **加上** §5.2 可执行示例。§1.3 树状摘要粗于 §5.2 时，以 §5.2 为准（尤其特殊产品分档到款）。
2. 现行释放视图、视图忠实稿、wiki、工作簿值域都不再作为规则正文。视图只可继续给 metadataReview 核对物理关系，不能改写优化方案公式。
3. 2026-09-05 V3 handoff（18 条请求）**作废为当前生成输入**。Agent1 必须发布新 catalog digest、新规则版本、新 handoff 批次；禁止原地覆盖。
4. SqlBot 不补公式、不把描述里的 Java 写成 SQL。缺少展开后的 queryRequirements 或规则树时阻断。
5. 优化方案目标是规则引擎 + 状态表，而不是再维护一套视图 SQL。Agent1 交付的是可求值规则与可查询事实；SqlBot 若编译一条只读 SQL，验收对齐该引擎，不对齐旧视图。

## Agent1 / businessRuleReview 必须修改

下列均属 RuleReader 新版本，不在 SqlBot 内修复。物理列批准仍属 metadataReview。

### A. 版本与来源身份

1. 新规则版本的 `sourceSha256` 等于固定包中优化方案文件哈希，不得继续使用与该文件不等的 draft/`catalogDigest`。
2. 把该版本写入规则版本存储，规则集合与交接必须同一精确版本。**2026-09-17 可行性核对更正**：现有 V3 集合实际为 `rule_versions_v3`；旧 `rule_versions` 未发现该版本不能证明 V3 未落库。Agent1 有旧 V3 历史落库记录，本轮未重读。若要求仍使用字面名称 `rule_versions`，必须增加迁移和 reader 版本分流，不能直接沿用当前入口；完整树可读取性还须独立补齐，见评估 F1。
3. 同一 `ruleVersion` 同时交出：完整规则树（阶段、优先级、outcome、短路）、事实目录、FactBindingRequest 批次。只交 18 条 `usages` 坐标不够。

### B. 禁止再把 §5.2 公式压成不透明 `source` 布尔

现交接把 R3/R4/R5/R6/R7/R8/合并组写成“eligible”布尔，描述里才有公式。新版本必须拆成可查询事实 + 规则条件引用这些事实。

### C. 事实目录增补（新 digest）

至少新增可绑定的基础事实，而不是把计算藏在一个 eligible 里：累计完工金额构成（抽提质检、任务单、报告释放金额）、到款含押金、未关联到款、押金、合同盖章枚举、框架/企业标志、完工日、开票状态、产品分档基准金额。合并组成员关系必须可查询。

金额口径按优化方案 §5.1/§5.2，不得从现行视图另抄一套容差公式。

### D. 规则树必须可独立求值

条件表达式引用上述事实，保留优化方案优先级：R0→R1→R9→R4→R2→R3→R8→R5→R6→R7，先前提后规则，命中即停。不得再用“单事实 eq true 即 READY”代替复合条件。

实施澄清：“命中即停”限定 eligibility 内部首个命中，不表示跳过合并组及 OA 后置约束；
各阶段终止及未知值语义须进入版本化交接并通过案例验证。现有求值器已有阶段区别，见评估 F4。

### E. 明确不是 Agent1 的工作

- 物理表列、JOIN、grant、snapshot、context 批准：metadataReview。Agent1 只提供可绑定的 mapping 候选与逻辑字段，不得假装已授权。
- 把规则编译成 SQL、AST 门禁、一条清单查询：SqlBot；须等本决策的新 handoff。
- 不把 wiki/视图稿公式混进新版本。
- 不覆盖 `0df35b35…` 批次或旧 candidate 哈希。

## 验收（Agent1 新版本）

- 源哈希 = 优化方案文件；`rule_versions` 与 handoff 同一 `ruleVersion`。
- 合成求值至少覆盖：报告标志四组；R3 标志真但分档到款假 → 不 READY；R1 四组；R9/线下为方案物理码而非 4/5；R8 第 N+1 天不命中当天相等支；R5/R6/R7 金额边界；合并组部分成员不满足 → 等待；D 规则集可独立交接。
- 无 `SOURCE_CODING_DIVERGENCE` 遗留到“未裁决”状态；复合 eligible 布尔从 catalog 移除或降为 derived（不进 SQL 生成）。
