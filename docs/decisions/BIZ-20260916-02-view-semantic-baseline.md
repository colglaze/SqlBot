## 权威分工

MongoDB 中精确规则版本及其不可变 FactBindingRequest 是生成输入；Agent2 应生成与该版本匹配的
事实 SQL 模板。规则可能变化，不能通过直接查询一个固定放行视图来代替规则驱动生成。

固定私有视图提供取数关系、物理编码、连接及既有计算表达的核对基准；工作簿用于定位和说明。
物理说明发生冲突时，以已选视图为本任务的参考基准。视图不能覆盖 MongoDB 中的规则条件、阈值、
分支或结构化空值策略，也不能把其全部业务过滤无条件带入所有事实查询。
事实取数必须保留规则判断所需的记录，不能先按旧放行条件过滤，再声称可以支持新规则。

- private commit：`2240e5bd18e36d17650896a10cc61e1c18e3daa0`。
- bundle digest：`6d403f1a110ea1699a72aec76f38be944583670f96767f5e3f44b2ac2e565160`。
- 当前主视图来源 SHA-256：`0fc47e0d9cbc1b2af213018e5922326c12a79c0c53295b907f61a7b3c567e230`。
- 其他来源逐文件身份使用固定包清单；来源变化必须建立新版本，不能混用后续部署定义。

该决定确定规则与物理来源的分工，不证明该视图版本已部署，也不产生数据库表列 grants、运行权限或
生产目录快照。私有原文与内部标识符仍不进入公开仓库、测试夹具、日志或模型请求。

## 当前差异的处理

- 原始标志的物理比较语义按视图核对，不能继续默认物理值与 MongoDB 事实枚举相同。
- 逻辑枚举与物理编码不同，需要明确的版本化绑定/转换；不得把 MongoDB 规则改成视图里的常量，
  也不得把旧原值查询误当成已完成转换。空值策略若冲突，记录具体输入差异并阻断该事实的真实生成。
- 共同前置条件、金额精度、容差、AND/OR 分组、时间和合并结果处理按当前规则请求逐项对齐。
  请求缺少结构化表达时形成上游版本化修订项，不从视图隐式追加或删除业务条件。
- 查不到记录返回零行、多条全部返回的用户要求保留；原 scalar 机器契约尚需独立对齐。
- 不把单个直接路径命中解释为最终放行，也不通过固定视图的旧过滤预先排除新规则所需的数据。

## 版本与实施边界

旧单字段候选、其用户审核记录和上游 handoff 均保留；不得把新语义直接写回旧 hash 对应的载荷。
原候选只能解释为历史原始取值查询，不能充当已验证的规则/物理语义一致模板。
新的可审阅材料必须明确标识版本和来源，并保持不可执行、未发布。

## 规则变化与验收方向

1. 按精确 ruleVersion/requestId 重读 MongoDB handoff，不用旧请求缓存冒充新规则输入。
2. 对新版本请求重新解析其需要的字段、filters、aggregation、timeRange、参数与完整 usages。
3. 使用对应批准版本的取数映射生成候选；业务值参数化，固定视图的旧常量不能替代新请求参数。
4. 重做静态/语义一致性校验，生成独立不可变候选供用户审核；不能继承旧版本的审核结论。
5. 变化后的结构超出当前生成能力时给出明确阻断，不静默退回固定视图或旧模板。

上述是用户要求下的实施方向，不表示当前已支持 JOIN/聚合/任意规则变化。现有 V3 受限单事实
生成范围仍按代码和进度说明；不在本次边界修正中宣称已实现完整生成能力。
本轮不连接 SQL Server，不执行视图，不调用在线模型，不改写 MongoDB 的规则或候选。
