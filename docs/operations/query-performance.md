# 查询性能与临时表策略

- 状态：`superseded`
- 替代决策：[BIZ-20260819-01](../decisions/BIZ-20260819-01-agent2-role-alignment.md)
- 适用范围：候选 SQL 的性能验证和分阶段计划

临时表不是默认答案。系统先证明单查询在预算内；只有复杂度或执行计划显示明显风险时，才生成受控的 `staged_script`。

## 1. 何时考虑分阶段

满足以下任一情况时进入性能复核，而不是直接认定需要临时表：

- 多个复杂规则重复扫描同一大表或重复计算同一子查询；
- 多个高基数 JOIN 后再做去重/聚合；
- 相关子查询、复杂 OR/NOT 或窗口计算导致计划不稳定；
- 基线 SQL 已有超时证据；
- `EXPLAIN` 的预计行数、扫描量、成本或阶段数超过项目预算；
- 受限试跑接近/超过超时阈值。

以目标数据库的 `EXPLAIN` 和实际受限试跑为主要证据，静态规则只用于预警。

## 2. 推荐分阶段方式

典型阶段：

1. `tmp_scope`：先按项目、时间和未释放状态裁剪基础集合；
2. `tmp_<condition_group>`：对高成本规则组分别计算业务实体主键和失败原因；
3. `tmp_violations`：合并并去重失败条件；
4. final SELECT：关联少量展示字段，按稳定主键分页；
5. cleanup：删除本次运行创建的全部临时对象。

每个阶段应只保留后续需要的列，尽早过滤、避免 `SELECT *`，并在一对多 JOIN 后明确唯一键。

## 3. 临时表约束

- 只允许目标数据库明确支持的会话级/本地临时表；
- 创建、使用和清理必须在同一个物理连接/会话；连接池不能在阶段之间换连接；
- 名称由服务生成并经过标识符校验，例如 `tmp_rsb_<run_token>_<stage>`，不能接受模型自由命名；
- 不包含原始敏感值、项目名称或用户输入；
- 使用 `finally`/连接回收钩子清理；数据库会话关闭仍应是第二层兜底；
- 禁止永久表和共享全局临时表；
- 临时索引、统计信息收集和事务语义按 dialect capability 显式允许，默认关闭；
- 每个阶段有独立 SQL 类型、依赖、预计行数、超时和可观测事件。

## 4. 安全执行预算

项目上下文至少配置：

- `planning_timeout_ms`；
- `statement_timeout_ms`；
- `max_result_rows` 和最大响应字节；
- 可选的最大预计成本/扫描行数；
- 最大临时表数量和预计磁盘占用；
- 总运行 deadline；
- 取消和清理 timeout。

超时后必须取消当前语句、使连接不可复用直至清理完成，并记录可能遗留的临时对象。不能无限自动重试昂贵查询。

## 5. 方言适配

临时表语法、`EXPLAIN`、超时和事务行为差异很大。每个 dialect adapter 必须声明 capability matrix，而不是仅替换 SQL 关键字：

```text
supports_explain
supports_explain_without_execute
supports_session_temp_table
supports_temp_index
temp_table_transaction_scope
statement_timeout_mechanism
cancel_query_mechanism
identifier_length_limit
```

未知方言或能力探测失败时，不生成临时表脚本。

## 6. 等价性验证

性能优化不能改变业务集合。对每个 staged plan：

- 使用相同合成夹具对比规则解释器期望结果；
- 在可行时与未优化参考查询比较主键集合；
- 验证重复消除不会掩盖多条失败原因；
- 覆盖 NULL、NOT、空集合和时间边界；
- 验证中途失败和正常完成都清理临时对象。

只有结果集合和失败原因等价，性能证据才有效。

## 7. 审核者应看到的性能证据

- 单查询与分阶段方案选择原因；
- 各阶段访问对象、预计/实际行数和耗时；
- `EXPLAIN` 的关键节点摘要，而不是只显示总成本；
- 临时表索引建议及其权限要求；
- 超时、结果限制、磁盘风险和清理结果；
- 与参考语义的等价性测试结论。
