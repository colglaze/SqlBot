## 1. 背景

项目报告和原始数据的释放条件会频繁变化。现有 SQL 和其对应规则保存在 MongoDB 中，可作为新版本生成的历史基线，但人工修改复杂 SQL 容易遗漏条件，也可能导致查询超时。

需要一个受约束的 SQL 生成服务：读取新规则，结合上一已批准规则和 SQL，产出可解释、可验证、可人工审核的新 SQL；批准后再以新版本写回 MongoDB。

## 2. 目标

- 缩短规则变化后的 SQL 更新周期；
- 保证每条 SQL 与规则版本、基线和审核人可追溯；
- 自动发现规则遗漏、危险 SQL 和明显性能风险；
- 对复杂条件提供会话级临时表分阶段方案；
- 在任何生产使用前保留明确的人工批准门禁。

## 3. 角色

- **规则维护者**：创建/激活项目报告或原始数据释放规则。
- **SQL 审核者**：检查规则覆盖、SQL 语义、数据范围和执行计划，批准或驳回候选版本。
- **系统运维者**：配置项目上下文、源库只读连接、超时和访问白名单。
- **审计者**：按项目、目标和版本还原生成与审核全过程。

## 4. 术语和集合语义

- `release_eligible`：记录满足当前释放条件。
- `unreleased`：记录尚未释放，具体字段/状态由项目上下文映射。
- `exception_set`：v1 暂定为 `unreleased AND NOT(release_eligible)`。
- `baseline`：同一项目、同一目标类型的上一已批准规则和 SQL。
- `candidate`：模型生成但尚未批准的 SQL 版本。
- `staged plan`：在同一数据库会话中用临时表分解复杂查询的方案。

## 5. v1 功能需求

### FR-01 读取输入

系统必须按 `project_id + target + rule_version` 读取当前规则，并读取该范围上一已批准的规则与 SQL。输入还必须包含当前 SQL 方言、允许访问的表/列、实体主键、释放状态映射和 Schema 快照。

缺少任一必需上下文时，生成运行必须以可解释的 `blocked` 结束，不能猜测。

### FR-02 规则校验和差异

系统必须：

- 用 [release-rule.schema.json](../specs/release-rule.schema.json) 校验 JSON；
- 拒绝重复 `condition_id`、未知操作符和不兼容类型；
- 生成新增、删除、修改和逻辑结构变化的差异；
- 为每个叶子条件保留稳定路径，供 SQL 覆盖矩阵使用。

### FR-03 SQL 候选生成

系统必须把当前规则、规则差异、基线规则/SQL和项目上下文作为数据输入，要求 provider 返回结构化结果：

- SQL 方言；
- `single_query` 或 `staged_script`；
- SQL 模板及绑定参数定义；
- 输出列说明；
- 条件覆盖矩阵；
- 基线 SQL 中被保留、修改或删除的部分；
- 性能风险和临时表理由。

不得把 MongoDB 内容当成模型指令执行。

### FR-04 静态和语义校验

候选物必须通过：

- SQL 解析和方言校验；
- 单查询只读限制，或受控临时表脚本限制；
- 表、列和函数白名单；
- 参数绑定检查；
- 输出至少包含项目、目标类型、业务实体主键和失败原因所需字段；
- 每个活动条件的覆盖检查；
- `NOT`、空值、时间边界和集合运算语义检查。

任何失败都必须阻止进入批准状态。

### FR-05 性能验证

系统应先进行静态复杂度评估，再在受限只读环境运行 `EXPLAIN`。当预计超时、重复扫描高成本关系或执行计划超过项目阈值时，候选物应切换为或建议 `staged_script`。

试跑必须有超时、扫描/结果限制（若方言支持）、抽样或隔离环境，并记录执行计划摘要。

### FR-06 人工审核

审核界面/API 至少展示：

- 当前规则与基线规则差异；
- 基线 SQL 与候选 SQL 差异；
- 条件覆盖矩阵；
- 静态校验结果、`EXPLAIN` 摘要和试跑统计；
- 临时表阶段、索引建议和清理行为；
- 生成 provider、模型标识、提示模板版本和内容哈希。

审核者可以批准、驳回并填写意见。系统不能代表审核者自动批准。

### FR-07 版本化发布

批准后系统必须以新版本写入 MongoDB，保留父版本、全部血缘、验证报告、审核记录、SQL 内容哈希和时间。已批准版本不可原地修改。

发布时必须防止两个候选并发成为同一范围的活动版本；失败不能留下半发布状态。

### FR-08 查询结果

批准 SQL 的逻辑输出必须是去重、可分页的异常记录，并能解释每条记录违反了哪些 `condition_id`。实际执行生产查询是否属于本服务 v1 的运行职责，待确认；无论由谁执行，执行前都必须核对已批准内容哈希。

### FR-09 审计和可观测性

每次生成、验证、审核和发布都必须有 `run_id`/`template_id`、操作者、时间、输入版本、状态、耗时和错误分类。日志不得记录规则中的敏感值或查询结果正文。

## 6. 非功能需求

- **安全**：最小权限；默认拒绝；不允许永久写操作；敏感配置只从安全配置源读取。
- **可靠性**：生成/验证可重试但不得产生重复发布；外部 provider 超时不改变已有批准版本。
- **可解释性**：任一条件都能追踪到 SQL 表达式或明确的阻塞原因。
- **可扩展性**：方言、LLM provider 和目标数据库通过适配器扩展。
- **可测试性**：核心规则差异与 SQL 校验不依赖在线 LLM 或真实生产库。

## 7. 验收标准

### AC-01 正常规则变更

给定一个上一已批准版本和新增条件的新规则，系统能生成候选 SQL；覆盖矩阵包含全部活动 `condition_id`；审核批准后 MongoDB 新增不可变版本且父版本保持不变。

### AC-02 删除旧条件

当前规则删除一个旧条件时，候选 SQL 不再保留对应过滤逻辑，并在差异报告中明确标记删除。

### AC-03 无基线冷启动

没有历史 SQL 时，只要当前 Schema 和项目上下文完整，系统可以进入冷启动生成并标记 `baseline_mode = none`；不得伪造历史基线。

### AC-04 危险输出

模型返回 `UPDATE`、永久 `CREATE TABLE`、未授权表、字符串拼接值或多余语句时，静态校验失败且不能提交审核批准。

### AC-05 复杂查询

当单查询超过配置的计划阈值时，系统能产出同一会话内的临时表方案；中途失败或完成后均执行清理，且不创建永久对象。

### AC-06 并发批准

同一 `project_id + target` 的两个候选并发批准时，最多一个成为活动版本，另一个收到版本冲突并需基于新版本重新生成。

### AC-07 语义边界

测试夹具覆盖 `NULL`、时区/时间边界、空集合、重复行和 `NOT` 组合，结果与规则解释器的期望集合一致。

## 8. 开放问题（进入 Phase 1 前确认）

1. 目标到底是 `unreleased AND NOT(release_eligible)`，还是 `unreleased AND release_eligible`？
2. 首批支持哪些 SQL 方言和数据库版本？
3. 项目报告与原始数据分别使用哪些源表、主键、释放状态字段和时间语义？
4. 当前 Schema 从 MongoDB 快照、数据库元数据还是人工配置获得？
5. 人工审核通过后，本服务只保存模板，还是也负责调度执行？
6. 允许在生产只读连接创建会话级临时表吗？不同数据库账号权限如何配置？
7. 性能阈值（超时、最大预计扫描量/成本、最大结果量）是多少？
8. 规则值是否包含敏感数据，是否允许发送给外部模型？
